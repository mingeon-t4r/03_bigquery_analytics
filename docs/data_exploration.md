# Day 1 — BigQuery 데이터 탐색

## 1. 분석 목적

Google BigQuery에서 NYC Citi Bike 공개 데이터를 탐색하고 원본 데이터의 구조와 분석 단위를 확인했다.
동일한 테이블을 조회하더라도 선택하는 컬럼에 따라 쿼리 처리량이 달라지는지 비교했다.

## 2. 데이터 소스

- 원본 테이블: `bigquery-public-data.new_york_citibike.citibike_trips`
- 데이터: NYC Citi Bike Trips
- 분석 도구: Google BigQuery
- 원본 Grain: Trip 1건

원본 테이블의 한 행은 한 번의 자전거 이용 기록을 의미한다.

### 주요 컬럼

| 컬럼 | 의미 |
|---|---|
| `starttime` | 자전거 이용 시작 시각 |
| `stoptime` | 자전거 이용 종료 시각 |
| `start_station_name` | 출발 Station 이름 |
| `end_station_name` | 도착 Station 이름 |

## 3. BigQuery 데이터 구조

분석에 사용한 공개 테이블의 경로는 다음과 같다.

`bigquery-public-data.new_york_citibike.citibike_trips`

BigQuery의 테이블은 Project, Dataset, Table의 계층 구조로 관리된다.

이번 분석에서는 Google Cloud의 공개 데이터 프로젝트에 저장된 NYC Citi Bike 데이터를 조회했다.

## 4. SQLite와 BigQuery 비교

| 구분 | SQLite | BigQuery |
|---|---|---|
| 주요 사용 환경 | 로컬 데이터베이스 | 클라우드 데이터웨어하우스 |
| 데이터 저장 | 로컬 DB 파일 | Google Cloud |
| 데이터 처리 | 로컬 실행 환경 중심 | 관리형 분산 쿼리 처리 |
| 주요 고려 사항 | 로컬 자원과 쿼리 효율 | 데이터 처리량과 비용 및 쿼리 효율 |

SQLite는 로컬 DB 파일을 직접 다루는 데 적합하며, BigQuery는 대규모 데이터를 SQL로 분석하는 관리형 데이터웨어하우스다.

BigQuery에서는 쿼리 실행 시 읽는 데이터량이 성능과 비용에 영향을 줄 수 있으므로 필요한 데이터만 조회하는 습관이 중요하다.

## 5. 컬럼 선택에 따른 쿼리 처리량 비교

동일한 원본 테이블에서 전체 컬럼을 조회하는 경우와 분석에 필요한 컬럼만 조회하는 경우를 비교했다.

| 조회 방식 | 보고된 처리 데이터량 |
|---|---:|
| `SELECT *` | 7.47 GB |
| 필요한 컬럼만 선택 | 2.51 GB |

전체 컬럼 조회보다 필요한 컬럼만 선택한 쿼리의 처리량이 더 작게 나타났다.

BigQuery는 컬럼 기반 저장 구조를 활용하므로 필요한 컬럼만 선택하면 읽어야 하는 데이터량을 줄일 수 있다.

이 결과는 해당 실습 쿼리의 처리량 비교이며 모든 쿼리에서 동일한 감소율이 발생한다는 의미는 아니다.

## 6. 기술적 검토

### 6.1 LIMIT과 처리량

`LIMIT`은 반환되는 결과 행 수를 제한한다.

하지만 `LIMIT 10`을 사용한다고 해서 항상 테이블에서 읽는 데이터량이 10행에 해당하는 크기로 줄어드는 것은 아니다.

따라서 BigQuery의 쿼리 처리량을 줄이려면 반환 행 수뿐 아니라 조회 컬럼과 필터 조건 및 테이블 저장 구조를 함께 고려해야 한다.

### 6.2 컬럼 기반 처리

`SELECT *`는 모든 컬럼을 조회 대상으로 지정한다.

반면 분석에 필요한 컬럼만 명시하면 불필요한 컬럼을 읽지 않을 수 있다.

이번 실습에서는 보고된 처리량이 7.47 GB에서 2.51 GB로 감소했다.

### 6.3 데이터 Grain

원본 테이블의 Grain은 Trip 1건이다.

따라서 월별 이용량, Station별 이용량 등의 지표를 계산할 때는 원본 Trip을 해당 분석 단위로 집계해야 한다.

이후 프로젝트에서는 Month × Station 단위의 Data Mart를 별도로 구축하여 분석에 활용했다.

## 7. 주요 결과

- NYC Citi Bike 원본 테이블의 구조와 주요 컬럼을 확인했다.
- 원본 테이블의 Grain을 Trip 1건으로 정의했다.
- 필요한 컬럼만 조회한 쿼리에서 처리량이 더 작게 나타났다.
- `LIMIT`에 의한 결과 행 수 제한과 실제 데이터 읽기량 감소를 구분했다.
- 이후 분석에서 쿼리 처리량과 데이터 Grain을 함께 고려할 필요성을 확인했다.

## 8. 분석의 한계

이번 실습의 처리량 비교는 두 조회 방식에 대한 결과이며 다양한 필터 조건과 테이블 저장 구조를 통제한 성능 실험은 아니다.

쿼리 실행 시간, 실제 청구 바이트 및 저장 구조 최적화의 효과는 이번 단계에서 종합적으로 평가하지 않았다.

Partitioning, Clustering 및 View를 활용한 별도의 처리량 비교는 프로젝트 후속 단계에서 수행했다.

## 9. 결론

BigQuery의 데이터 구조와 원본 Grain을 확인하고 컬럼 선택에 따른 쿼리 처리량 차이를 관찰했다.

대규모 데이터를 분석할 때는 필요한 컬럼을 명시적으로 선택하고, 분석 목적에 맞는 Grain을 정의하며, 쿼리 처리량을 검토해야 한다는 점을 확인했다.
